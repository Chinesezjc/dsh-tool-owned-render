# Agent Note: Tool-owned render increments on ui-tool — layout primitives, a unified lamp, and a structured bash result

Status: proposed

English | [中文](2026-08-03-unified-list-of-blocks-tool-render.zh.md)

## Problem

The [Client Tool presentation ownership](../../implemented/architecture/2026-08-08-client-tool-presentation-ownership.md) decision landed `@deepseek-ai/dsh-client-ui-tool`: [ToolCallTree](../../../../packages/client/ui-tool/src/client/tool/ToolCallTree.tsx) recursively composes root/subcalls, every atomic tool renders through the keyed `tool.call.toolview` slot dispatched by wire tool name, [GenericToolCard](../../../../packages/client/ui-tool/src/client/tool/toolviews/GenericToolCard.tsx) is the fallback, and per-tool card models live beside them. That ownership boundary is not in question here; this note is an increment on top of it. Four things are still unresolved inside the atomic tool views:

- **Status is derived twice, and the `*_ABORTED` family reads as failure.** `toolRowModel` derives the row state ([tool-call-model.ts:199-201](../../../../packages/client/ui-tool/src/client/tool/models/tool-call-model.ts#L199)), and then both [GenericToolCard.tsx:45](../../../../packages/client/ui-tool/src/client/tool/toolviews/GenericToolCard.tsx#L45) and [bash-sample.tsx:64](../../../../packages/client/ui-tool/src/client/tool/toolviews/bash-sample.tsx#L64) re-derive the same terminal-failure override ([terminalFailed](../../../../packages/client/ui-tool/src/client/tool/models/terminal-card-model.ts#L72)) on top — the same two-step derivation written twice. `ToolRowState` maps only `interrupted` to amber ([tool-call-model.ts:20](../../../../packages/client/ui-tool/src/client/tool/models/tool-call-model.ts#L20)); a cancelled tool that settles its own `*_ABORTED` code (`TOOL_ABORTED` from [tools/index.ts:1650](../../../../packages/core/tools/src/index.ts#L1650), `FS_ABORTED`, `WEB_ABORTED`, …) lands `isError: true` → red, indistinguishable from a crash, and a timed-out bash command settles a non-zero exit → red the same way (`timedOut` never reaches the lamp at all).

- **No shared card shell.** Every registrant hand-rolls its row: [bash-sample.tsx](../../../../packages/client/ui-tool/src/client/tool/toolviews/bash-sample.tsx) owns its own CSS module and a hardcoded IN/OUT `ioCard` (:134-152); the read/search/web registrants drive the shared [ToolRow](../../../../packages/client/ui-tool/src/client/tool/components/ToolRow.tsx) chrome, but the expanded body is still ToolRow's single-card-kind chain (:159-160) plus a hardcoded text `ioCard` (:271-289). There is no reusable `Segment`, so a tool that wants a lamp, line numbers, per-segment scroll, or per-segment copy re-implements each. `grep -rn CardShell` is still 0.

- **Registration is boilerplate seven times.** Each built-in registrant writes the same `ctx.slots.inject('tool.call.toolview', () => ctx.slots.register({ ... }, Component))` stanza, one per row module in [`toolviews/`](../../../../packages/client/ui-tool/src/client/tool/toolviews/) — seven of them, e.g. [bash-sample.tsx:178](../../../../packages/client/ui-tool/src/client/tool/toolviews/bash-sample.tsx#L178). The toolview-dissolution note's regret clause — build the facade once registrants reach three-to-five or a bulk-registration pattern appears — is tripped: there are seven, and the targeted fan-out an interaction registrant needs (`ask_user_question`/`todo_write` render only a transcript summary in chat, not a details/preview card) is not expressible through the raw stanza.

- **bash still round-trips its exit status through text.** `presentBashResult` calls `parseExitStatus` on the rendered result to split the `[exit code: N]` / `[killed by signal: X]` marker back off ([tool-bash/index.ts:124-136](../../../../packages/bash/tool-bash/src/index.ts#L124)), so the terminal result view carries `exitCode`/`signal` but not `timedOut` — the canonical bash result does carry it ([index.ts:168](../../../../packages/bash/tool-bash/src/index.ts#L168)), but that is the execution-local canonical value, not the view. A timed-out command is therefore indistinguishable from a crash everywhere the lamp or the exit pill reads the view.

The precipitating need remains the interactive, multi-command bash this note's earlier draft named: a single bash call runs several commands, and a persistent/interactive session exchanges stdin/stdout in rounds. Today each such shape is a fresh bespoke variant (the bash registrant's `ioCard`, the persistent shell's no-meta text path) rather than a composition of shared parts.

## Proposal

This is an increment on the implemented ui-tool boundary, not a replacement of it. ui-tool keeps `ToolCallTree` recursion, the keyed `tool.call.toolview` dispatch, `GenericToolCard` as the render-site fallback, the card models, and the details output — the [08-08 ownership table](../../implemented/architecture/2026-08-08-client-tool-presentation-ownership.md) is unchanged. What this note adds is the shared layer *under* the atomic views plus the two tool changes that need it:

1. **`registerToolView(ctx, { key, locale, inject?, views? }, component)`** — the facade the [toolview-dissolution note](../../implemented/architecture/2026-07-23-toolview-dissolution.md) deferred with a regret clause, now built because ui-tool's seven registrants are its natural users. It forwards `slots.register`'s options (the `locale` seat and optional `inject` factory) and fans one component across the toolview slots named in `views` (default: all declared per-view slots — chat, details, and PR 3's preview; the fan-out re-evaluates when a slot is declared, so PR 2's and PR 3's slots are covered as they land). An interaction registrant whose chat row is only a transcript summary sets `views: ['chat']`. It stays sugar over `slots.register` — slot-name narrowing, tool→key vocabulary, props pre-composition, the targeted fan-out — with no parallel registry, honouring that note's one-registration-model decision.
2. **Layout primitives `ToolCard` / `Segment` (and deferred `Group`)** a tool composes, replacing each registrant's hand-rolled row and ToolRow's hardcoded card chain and `ioCard`.
3. **A unified lamp helper** — one observable-status derivation every registrant feeds, replacing the two-step `toolRowModel.state` + `terminalFailed` duplication.
4. **A structured bash `presentationMeta`** so `presentBashResult` stops parsing the `[exit code: N]` marker back off rendered text and the lamp sees `timedOut`.

Increments 2 and 3 live in a new package, `@deepseek-ai/dsh-client-tool-render`, a **plain platform lib** (shell-bundled, no per-fiber HMR — the deal `ui-primitives` has today, and the right deal for tool-neutral leaf code with no product behaviour), registered in the platform-module seed table ([platform.ts `PLATFORM_MODULES`](../../../../packages/client/web/src/platform.ts#L8)) so its exports are statically value-importable by `ui-tool` and third-party registrants alike. Increment 1 (`registerToolView`) lives in `ui-tool`, beside the `tool.call.toolview` slot declaration it sugar-coats: it must operate on that slot's typed props, and a platform lib must not depend on a graph plugin's slot types. The built-in registrants that consume the facade stay where they are, in `ui-tool` (a `dshClient` graph plugin), because a registrant carries product behaviour and must be a graph row for the boot graph and per-fiber HMR. `ui-tool` keeps the card models and the atomic views; it adds a dependency on the render package and re-writes each built-in registrant to compose the primitives through the facade.

There is **still no central render dispatch and no client-side render-kind union.** Per view, that view's keyed toolview slot *is* the dispatch — ui-tool's implemented arrangement, unchanged. The registry of registrants is shared across the per-view slots via `registerToolView`, so the chat stream, the details panel, and PR 3's preview panel render a tool through the same registrant. The isolation claim is unchanged from the earlier draft and now holds inside the atomic views: **changing** an existing tool's rendering edits only that tool's registrant module (its component and its wire→props, depending only on the render package's primitives, touching no central switch and no other tool); a **third-party** tool ships its own `dshClient` plugin that mounts its own registrant through the raw slot stanza (`ctx.slots.inject('tool.call.toolview', …)` plus `ctx.slots.register`, the exact form the built-ins write today) — the facade is sugar for ui-tool's own registrants, and a third-party plugin cannot value-import a sibling plugin's exports under the client bundle purity gate, so the facade stays out of its reach while the underlying slot registration stays the one registration model for everyone; **adding a built-in** is one `registerToolView` call in the assembler.

The host-side view vocabulary is untouched. `presentCall`/`presentResult` still return the closed `ToolCallView`/`ToolResultView` unions in [presentation.ts](../../../../packages/core/tools/src/presentation.ts) — the one host→client projection present on both live and replay paths. A tool whose data fits an existing view variant needs no central change; a tool needing a genuinely new structured payload extends that closed union exactly as it does today. The `presentationMeta` channel is likewise unchanged; increment 4 makes bash *use* it, it does not extend it. The one concrete union change is the `timedOut` projection: today `TerminalResultView` carries only `output`/`exitCode`/`signal`, so a timed-out command cannot reach the lamp through the view. PR 1b extends `TerminalResultView` with a `timedOut` field, projected by `presentResult` from the structured meta — the closed-union extension path this paragraph already allows — so the lamp reads it from the view, never from the raw meta.

An interactive prototype validating the visual shapes (all tool shapes, the stress cases) lives on the orphan assets branch `list-of-blocks-assets`, not in the tree, as `unified-list-of-blocks-mock.html`. It is a one-time design artifact — the note text, not the prototype, is the authority for what ships.

### The primitives: ToolCard / Segment / Group

The package exports composable parts, not a mandated hierarchy. A tool's component picks what it needs:

```
ToolCard   — the card frame (border, padding, the transcript row shell)
  Segment  — one IN or OUT content unit: a [gutter][body] grid with an
             optional lamp, optional line-number gutter, per-segment scroll
             and copy. This is the core unit; most tools compose Segments
             directly.
  Group    — OPTIONAL. Bundles several Segments under one lamp, for a tool
             with more than one observable execution unit (multi-command
             bash; interactive rounds). A single-execution tool never uses it.
```

- `Segment` is the only part most tools touch. `read` is `ToolCard` → an IN `Segment` (path + range) → an OUT `Segment` (numbered lines). No `Group`.
- `Group` is used only when a tool genuinely has multiple execution units in one call. It carries the lamp for that unit; nesting Groups (a recursion) is deferred (§recursion). No PR 1–3 producer emits a `Group` — a multi-command call composes Segments directly, and each interactive round is its own card — so the `Group` primitive itself is **deferred to its first producer** (the Later per-command capture / round grouping), landing with the behaviour it serves rather than shipping as an abstraction nothing yet feeds. It stays in the vocabulary here so the type and layout are designed before that producer arrives.
- `ToolCard` is the frame. A tool that wants to restructure its whole row draws its own frame with `ToolCard` (or replaces it); a tool that wants the standard row uses the default-composition helper. Row-frame consistency across tools is a convention the built-ins follow, not a lock.

The names deliberately avoid the two collisions the earlier draft hit: they are **not** the `*Block` leaf family (`TerminalBlock`, `ReadBlock`, … remain the content renderers a Segment may embed), and `Group` is **not** the session model's `Turn` (`turn/start`/`turn/end`).

Vocabulary is tool-neutral: the primitives know only `Segment`, `role: 'in' | 'out'`, an optional lamp, and the tool-supplied content — not shell words (`command`/`cwd`/`exitCode`), because the same parts must carry a file read, a diff, a search query, and a fetched URL.

### The lamp: one observational derivation, offered as a helper

The package exports one lamp-state function over what the harness can observe; a tool's registrant feeds it the result and hands the state to a `Segment` or `Group`. It replaces the two-step duplication in `GenericToolCard`/`bash-sample` (the problem statement counts five encodings overall — ui-skill's `SkillRowState` is the fifth — but it is a row-level state for the skill interaction row, tool-owned by design, not replaced by the lamp helper). A tool may pass its own state, but the shared helper is what makes every tool agree. The helper checks in order — specific signals *before* the generic `isError` rules, because both a cancelled result and a failed terminal command carry an `isError` value the generic rules would mis-read:

- **cancelled or interrupted → amber (warn).** Cancellation surfaces two ways, both amber. The dispatch-level abort the registry mints — `error.info.code` = `ABORTED` (a started body that throws the generic abort, e.g. bash's `TOOL_ABORTED`) or `ABORTED_BEFORE_DISPATCH` ([tools/index.ts:1650/:1664](../../../../packages/core/tools/src/index.ts#L1650)). And the **tool-owned abort code** a cooperatively-cancelled tool returns as its own `isError` result, which the registry preserves rather than rewriting to `ABORTED`: `FS_ABORTED` (read/write/edit), `SEARCH_ABORTED` (grep/glob), `WEB_ABORTED` (web), `ASK_ABORTED`, `SESSION_QUERY_ABORTED`. The helper matches the whole `*_ABORTED` family plus the client-synthesised `interrupted` code the `stopped` row state reads ([history-fold.ts:266](../../../../packages/client/runtime/src/client/session-history/history-fold.ts#L266)), so a cancelled read, grep, web, or bash all map to amber. It runs on the client node, where `appendToolResult` has flattened the server's `error.info` onto the event's `error` — so it reads the code at `block.error.code`, not the server-side `error.info.code`. Checked first, because a cancelled/interrupted result settles `isError: true` *and* carries the code — the generic error rule below would mis-map it to red.
- **terminal-card tools refine on exit signals** (bash, and `tool-pwsh` on Windows, which carry the same exit/signal/timeout fields and settle a non-zero exit with `isError: false`): `timedOut` → amber; a terminating `signal` not from our timeout/abort → red (a crash `SIGSEGV`, or an external `SIGTERM`); else the exit code decides (`0` → green, non-zero → red). Checked before the generic success rule, because a non-zero exit settles `isError: false` and would else read as green. The `timedOut` arm depends on increment 4: today `timedOut` never reaches the client view, so until bash's structured result lands, a timed-out command reads as a signal/exit red — a documented bounded gap, closed by PR 1b.
- **running → blue** (the `ongoing` pixel-chase dot).
- **generic — every other tool: `isError === false` → green (done), else → red.** Completion is itself the observable signal; this is the base rule, reached only after the specific checks above.
- **grey (neutral)** only where an outcome is genuinely unobservable — an interactive-shell round whose outcome has no structured channel yet (below). The helper never parses a Traceback to invent a red lamp for something it cannot observe.

Attribution uses only the harness's own signals, never a guess at who sent an OS signal. A single-shell bash command aborted mid-run persists `ABORTED` — the tool throws `HarnessError('tool call aborted', TOOL_ABORTED)` ([tool-bash/index.ts:385](../../../../packages/bash/tool-bash/src/index.ts#L385), pre-dispatch arm at :360) — so it is amber on replay with no deferred change. The client-synthesised `interrupted` code maps to amber too. Three settled-abort shapes remain code-less and render red until their own PRs: a persistent-shell round abort ([tool-bash-persistent/index.ts:322-323](../../../../packages/pty/tool-bash-persistent/src/index.ts#L322)), a raw-PTY send abort ([tool-pty/index.ts:279](../../../../packages/pty/tool-pty/src/index.ts#L279)), and the persistent shell's caller abort after queueing ([tool-bash-persistent/index.ts:393](../../../../packages/pty/tool-bash-persistent/src/index.ts#L393)) — `exec.signal.throwIfAborted()` throws a bare `DOMException` `AbortError` that `toolErrorResult` ([tools/index.ts:1594-1601](../../../../packages/core/tools/src/index.ts#L1594)) converts with no `info` code, so it too renders red with no distinguishable code; making them amber needs each to persist a distinguishable code.

`neutral` (grey) is the one state new to the `StateDot` members: `warning` (amber) is already a `StateDotState` member with a CSS rule (the `stopped` row uses it), so the helper returns the existing `warning`; only grey needs a new member and rule. The lamp is colour-only and `aria-hidden`; each carries a matching accessible status text (the row's `stateStatus` pattern), so done/error/running/warn/neutral survive without colour.

### What a Segment gives a tool

A `Segment` is a `[gutter][body]` grid; the tool supplies the body, and the primitive provides the shared mechanics so no tool re-implements them:

- **Gutter, mutually exclusive by role.** An IN segment's gutter carries the **lamp** (far-left, first row only); an IN segment **never carries line numbers**, even when many lines (a heredoc script, a `run_code` program body, a big args JSON) — those lines are input, not file content. An OUT segment's gutter carries **line numbers** (right-aligned) only for OUTs that show *file content* (read, grep, diff); a diff's gutter shows real old/new line numbers, **not** `+`/`-` marks (red deletes / green adds colour the number and body; a deleted line and its replacement may show the same number). A diff's real old/new line numbers require the `FileDiff` payload to carry them — today it holds only `path`/`oldText`/`newText` and hunk computation drops `oldStart`/`newStart` — a presentation-contract extension staged with the write/edit migration in PR 2. Non-file OUTs (bash output, web body, args JSON) leave the gutter empty.
- **One gutter width per `ToolCard`**, `max(lamp-min, widest line number)`, so every Segment's body starts on the same line; adaptive to a 6-digit number. Line numbers are always visible, never hover-hidden.
- **Per-segment scroll**: a Segment over a height cap becomes a fixed-height scroller; line numbers scroll with the body, the lamp is pinned to the non-scrolling shell. Long lines overflow horizontally; indentation is never folded. The scrollbar reuses ui-theme's themed-scrollbar token pair (`--dsh-scrollbar-thumb`/`-hover`) rather than a self-drawn overlay, following [the pointer-revealed-scrollbars note](../../implemented/feature/2026-08-04-pointer-revealed-sidebar-scrollbars.md): `transparent` at rest, the surface's l2 pair while pointed at, over the reserved gutter ([reserved-gutter note](../../implemented/bug-fix/2026-07-28-themed-scrollbars-and-reserved-gutter.md)) so nothing shifts. A drawn thumb on an elevated surface uses the l2 pair; a resting `transparent` thumb draws nothing so owes no l2 — the *hiding no longer counts as elevating* clause.
- **Per-segment copy** (IN and OUT each have one — copying command and output are separate; there is no whole-card copy). Controls anchor to the segment's non-scrolling top-right, revealed on hover / `:focus-within` / touch.
- **Type sizes** match the existing cards (the 13px/22px `--dsw-font-*` code-block tokens), per design review.
- A segment renders **no** verb badge (`READ`/`WRITE`): the tool row's icon and title already name the tool.

Empty and input-less segments collapse symmetrically: an empty OUT collapses its height to zero but keeps its border (two adjacent divider lines — "output region, empty"); an input-less OUT (a generic console dump) carries the lamp itself on its first row and has no command row.

### Each tool as a registrant

Each built-in tool is a self-contained registrant module: a React component that composes the primitives and does its own wire→props, registered through the facade. The table is what each tool's component renders — not a set of central "kinds":

| Tool | IN | OUT | Lamp |
|---|---|---|---|
| bash (1 cmd) | prompt line: cwd + command | output text (no line numbers) | exit/signal/timeout/abort |
| bash (N cmds) | the raw `command` as one prompt line (single `command`; per-command split is the deferred executor change) | merged output | no `Group` today — one observable result, one lamp, Segments composed directly; per-command `Group`s need the deferred executor change |
| bash (interactive) | prompt line for the round | round output | each round is its own `bash` call; per-round done/error needs the persistent tool's canonical value to retain the round exit code first (today it reaches persisted data only as the non-zero `[exit code: N]` marker, and `tool-bash-persistent` has no structured result) — deferred; grey until then |
| read | path + line range | numbered file lines | done/error |
| write / edit | `path` | applied diff, real (old/)new line numbers | done/error |
| grep | query + scope | match groups (line numbers) + recovery locator (2nd OUT) | done/error |
| web_search | query | answer + numbered source list (clickable `http(s)`-only links, reusing `SafeLink`) | done/error |
| web_fetch | url | status line (1st OUT) + fetched body (2nd OUT) | done/error |
| generic (fallback) | args JSON | result text | done/error |

A **running** call renders with a pending OUT and a blue lamp; the IN comes from the tool's call view (`terminal`'s command/cwd, `diff`'s `FileDiff`, `read`'s `kind`/`locations`). A call view carrying only a `title` renders that title as the running IN — a bounded reduced-fidelity case each tool closes by enriching its own `presentCall`, not a new view. write/edit keep the running-state call-time diff (the intended change as the OUT while in flight, replaced by the applied diff at settle); the running-state diff carries **no line numbers** — `oldStart`/`newStart` exist only in the executed hunk's metadata, which `presentCall` cannot know, so the real old/new gutter appears only at settle (the settled diff's line numbers come from the extended `FileDiff` payload of the migration). The code variant's program body (`run_code`, `cordis_mount`) renders as a monospace, syntax-highlighted IN segment (no line numbers) reusing the repo's shiki integration; the highlight needs a language — `run_code`'s `presentCall` carries only `title`/`kind`/`rawInput` with no language hint ([code-mode.ts:643-648](../../../../packages/core/tools/src/code-mode.ts#L643)), so the registrant keys the Shiki grammar off `kind` when it distinguishes the language (TypeScript vs Python), falling back to plain monospace when it cannot.

### Two paths for a tool, no declarative middle

There are exactly two ways a tool reaches the UI:

1. **Write a component (the main path).** The tool's registrant composes the primitives — full control, restructurable in isolation. Built-in tools use this; a tool that wants convenience composes the default helper; a tool that wants to restructure everything draws its own `ToolCard`.
2. **Generic fallback (zero code).** A tool with no registrant renders as IN = args JSON, OUT = result text through the slot outlet's `fallback` (the assembler passes `GenericToolCard` as `opts.fallback`; keyed registration requires a concrete `key`, so the generic path is the render-site fallback, not a registered component) — so it still gets the lamp, gutter, scroll, and copy, instead of today's threadbare `ioCard`.

There is **no central render-kind union and no declarative middle tier.** A closed union of render kinds with a central `assertNever` switch was considered and rejected: adding a kind is a compile-breaking change at the shared switch, which is exactly "you cannot change one tool in isolation". Tools that want to share content rendering **compose** the existing leaf components (`ReadBlock`, `DiffBlock`, `TerminalBlock`, `CodeBlock`) inside their Segments; that is composition, not a central switch.

### Data source: the text-reconstructable boundary is preserved

Whether a tool needs structured data beyond the model-facing result text is unchanged by this work. bash can reconstruct `command` and exit from args and output — and `cwd` from the call view's workdir as resolved by the bridge against the session cwd (a relative or omitted workdir resolves in the executor/bridge, which a pure presenter cannot see) — which is why it is the one card that does **not** use `presentationMeta` today (it gains one here, replacing its `parseExitStatus` text round-trip). read's line numbers, search's groupings, and web's sources are lossy in text, so they ride `presentationMeta` — the only structured channel that survives replay, since `ToolEventView` is never persisted. A registrant reads the tool's call/result view (the client never sees `presentationMeta` directly; it is the host-side projection input). The invariant **Model-visible ⟺ logged** ([AGENTS.md §Conventions](../../../../AGENTS.md#conventions)) holds: the model sees flattened text, the UI sees the structured view, both from the same execution. A `run_code` sub-call is a shape the channel does not cover: `presentationMeta` is skipped for it and `tool/code-dispatch` records only arguments/isError/content ([code-mode.ts:508-517](../../../../packages/core/tools/src/code-mode.ts#L508)), so the client's sub-call views are null ([tool.ts:90](../../../../packages/client/ui-conversation/src/client/conversation-nodes/tool.ts#L90)) — but the sub-call still dispatches through the same keyed toolview slot, so a registered key claims it with null views and the lamp can only report what the null-view shape exposes (`isError: true` → red). The null-view sub-call shape is unowned until PR 1b adds it; until then a cancelled sub-call honestly reads red, never amber, because nothing persists its abort code.

### Recursion is deferred entirely

Nesting `Group`s — a group of executions folding into one collapsible unit with an aggregated lamp — is **deferred entirely, no field in the type**: no aggregation rule, no recursive renderer, no group summary. It would need status aggregation across the five lamp states, a group-title source bash does not provide, and a localized fold summary — none of which the motivating needs (multi-command, interactive) require. When built, it lands as a compile-breaking type extension alongside its consumer.

### Migration shape

**PR 1 — the package + primitives + bash + one tool.** A stacked PR series (each step bases on the previous), one concern each:

1. **Create `@deepseek-ai/dsh-client-tool-render`** (plain platform lib) with the primitives (`ToolCard`, `Segment`, the deferred-`Group` vocabulary, the default helper) and the lamp helper. No behaviour change: nothing consumes them yet, and ui-tool is untouched.
2. **bash** converted to a registrant composing the primitives, with a new bash `presentationMeta` carrying the structured result (command, output, exit/signal/timeout/timedOut — cwd stays out of the projection: `presentationMeta` is a pure function of args and the canonical value, and the canonical bash result carries no cwd, so the resolved workdir never enters the value; cwd renders from the call view as the bridge resolves it against the session cwd). First real tool — the snapshot/e2e coverage that needs real tool data lands here. A multi-command call composes Segments directly under one lamp today, no `Group` (per-command `Group`s are the deferred executor change). Registering a `bash` component suppresses the unregistered-fallback for **every** `bash` result, so this one registrant must cover all of bash's shapes, not only the structured foreground one: (a) the structured foreground result via the new meta; (b) `tool-bash-persistent`, which also registers the tool name `bash` and carries no `presentationMeta` (plain-string output, `render` only), via the **no-meta text-reconstructable path** — command from args and exit from the `[exit code: N]` marker, but **not cwd**: a persistent shell that ran `cd` leaves its current directory in none of args, output, or the session cwd (only the initial workspace), so it cannot be reconstructed there, and since the structured meta never carries cwd (it is a pure projection of args and the canonical value), the persistent shell's cwd stays omitted — the registrant must not render the bridge's default resolution, because an omitted workdir resolves to the session's *initial* cwd ([terminal-card-model.ts:89](../../../../packages/client/ui-tool/src/client/tool/models/terminal-card-model.ts#L89)), which is wrong after `cd`; (c) a `run_in_background` call, whose call/result view go through `generic` with a task id today and whose polling/task-id shape the registrant must render since the generic fallback no longer fires; (d) a `run_code` sub-call, whose call/result views are null — the registrant must render the null-view shape so the sub-call row stays honest (it cannot yet be amber: nothing persists the abort code, see the data-source section); and (e) a **failed foreground call**, which `presentBashResult` renders as a generic error view (spawn, approval, or execution failure — `isError` settles a generic card, not the structured terminal card, [tool-bash/index.ts:124-135](../../../../packages/bash/tool-bash/src/index.ts#L124)), so the registrant must render the error text through the generic fallback, not assume every `bash` result carries the structured shape. PR 1b tests all five. It must not assume the new meta exists or delete `parseExitStatus` — the `@deepseek-ai/dsh-bash` seam export outlives PR 1b, since `tool-pwsh` consumes it ([index.ts:29](../../../../packages/bash/tool-pwsh/src/index.ts#L29)) until its own PR 2 migration. `tool-bash-persistent` is not a consumer — it depends on no bash package and writes the `[exit code: N]` marker itself ([index.ts:177](../../../../packages/pty/tool-bash-persistent/src/index.ts#L177)), which is why its no-meta path reconstructs exit from the marker text rather than from the shared parser.
3. **`registerToolView` in ui-tool + adoption (PR 1c)**: implement the facade beside the slot declaration it sugar-coats, then re-write the seven built-in registrants through it — the targeted fan-out for `ask_user_question`/`todo_write` (`views: ['chat']`) lands here. Mechanical, no visual change; each registrant's component is unchanged (the facade is sugar over the raw stanza they already write).
4. **One more tool** (read or search) converted, proving the primitives are genuinely tool-neutral, not bash-shaped; its own snapshot/e2e.

**PR 2 — convert the remaining tools; fold the primitives into the generic path.** Convert each remaining tool to a self-composed registrant — read/search leftover, write/edit, grep/glob, web_search/web_fetch, the code variant `run_code`/`cordis_mount`, and `tool-pwsh` (same terminal shape); `str_replace_editor` and `terminal_send` are live view producers with no keyed registrant today, so each must gain one (or an explicit degradation to the generic fallback) in the same step that retires ToolRow's single-card-kind chain — otherwise their rows silently degrade; the persistent-shell and PTY tools follow once they gain a structured per-round result. Then **retire the central card-chain**: the `ToolRow` card-kind ternary (:159-160) and its hardcoded `ioCard` (:271-289) go — the details panel keeps its own per-view slot and renders the shared registrants through it, so each view's toolview slot is the only dispatch *within that view*. Retire the per-block `.block` geometry and the duplicated cap/copy code; unify the `CHAT_*` constants; fold i18n into one labels surface. Each conversion also owns its `run_code` sub-call shape: PR 1b defined the null-view shape for `bash` (shape d), and every later registrant claims its sub-calls through the same keyed dispatch, so each PR 2 conversion must render (or explicitly decline) its own null-view sub-call rows the same way. Delivered as a per-tool-group stack (write/edit; grep/glob; web) since a single ~8–10k-line PR would be unreviewable.

**PR 3 — side preview panel.** A resizable, right-docked, singleton preview container (click-to-replace, with a second-level expand to true fullscreen), evolving today's `DetailsPanel` Output pane, opened by a per-segment `⤢` button. It declares its own per-view toolview slot and renders a tool's own registrant through it (not a separate dispatch), so it inherits every tool's presentation for free. Separate, lower-priority; the earlier PRs neither render nor reference it.

**Later** — per-command `Group` capture for a joined multi-command call and a structured per-round result for the persistent/PTY tools (both executor/backend changes the primitives already admit — a producer emits more `Group`s / a value retains the exit code), nested-`Group` recursion and the per-behaviour status shapes (streaming, background tasks, approval-required, sandbox denial — new fields, each a compile-breaking extension alongside its consumer), codes for the currently code-less abort shapes, which would make persistent/PTY aborts amber, and the persisted abort code for `run_code` sub-calls, which would make a cancelled sub-call amber. Each lands with the behaviour it serves.

This note's owning work is PR 1; PR 2 (full conversion + central-card-chain retirement) precedes PR 3 (side preview panel).

## Alternatives considered

- **A central skeleton that owns rendering, tools supplying declarative render kinds.** This was the earlier draft: one `Block`/`Turn`/`Segment` skeleton with a closed render-kind union and an exhaustive `assertNever` switch; tools describe their segments by picking kinds. Rejected against the isolation claim: adding or changing a kind is a compile-breaking edit at the shared central switch, so a tool's presentation cannot change in isolation. The tool-owned model keeps the same *visual* result (composed primitives) without the central coupling.

- **Fold the primitives and lamp into `ui-tool` directly, no new package.** Rejected: ui-tool is a `dshClient` graph plugin (per-fiber HMR, boot graph), the right home for registrants that carry product behaviour but the wrong home for tool-neutral leaf code — a shell-bundled platform lib updates on a shell rebuild and is statically value-importable by third-party registrants without joining the plugin graph. The platform/plugin split `ui-primitives` already models stays.

- **Extend only bash to multi-command, leave the other cards alone.** Rejected: the "status lives outside the card", "no shared IN/OUT", and "registration boilerplate" problems are shared across tools, not bash-specific.

- **A flat `Segment[]` stream, no `Group`.** Rejected: it deletes "which segments belong to one execution" from the data, forcing the renderer to infer grouping; interactive sessions (one process, many rounds) then cannot be distinguished from independent commands. `Group` is optional but carries that fact when present.

- **A mandated central card shell tools slot into (chrome fully owned centrally).** Rejected: it constrains a tool to the shell's arrangement. The package instead exports parts a tool composes, with a default helper for the common case — consistency by convention, not by lock.

- **Per-tool sibling packages (each tool ships its own render package).** Rejected as too heavy: backend tool packages cannot import React, so each would need a sibling client package. One render package plus per-tool registrant modules in ui-tool gives the same isolation (edit one module) at a fraction of the package count.

- **A global registrant registry the panels query directly (side-channel lookup).** Rejected: it would let the details/preview panels resolve a tool's component by tool name outside the slot system — bypassing registration-as-effect, disposal, and session scope, and inviting the cross-plugin component import / `ReactNode` passing the slot contract forbids. The per-view toolview slot family plus `registerToolView` gives every panel the same registrants while staying inside that contract; the registry *is* the slot, queried through each view's own render site.

- **Expand as a centred modal / fullscreen takeover.** Rejected in favour of the resizable right-docked side preview panel (singleton, click-to-replace, optional second-level fullscreen) plus per-segment scroll; the panel keeps the conversation visible and reuses each tool's registrant.

- **Self-drawn overlay scrollbar.** Rejected — the same call [the pointer-revealed-scrollbars note](../../implemented/feature/2026-08-04-pointer-revealed-sidebar-scrollbars.md) made: it costs hit-testing, drag, wheel, momentum, and both palettes' hover states for a cosmetic gain. The primitives reuse ui-theme's token indirection instead.

## Acceptance criteria

- `@deepseek-ai/dsh-client-tool-render` exists, holding the `ToolCard` and `Segment` primitives + default helper (the `Group` primitive lands with its first producer) and the lamp helper; `ui-tool` depends on it and mounts the toolview slots as it does today. The package creation (PR 1a) changes no behaviour and no pixels (snapshot unchanged).
- bash and one other tool render as registrants composing the primitives; the two-step status derivation in `GenericToolCard` and `bash-sample` is replaced by the one lamp helper for those two tools (ui-skill's `SkillRowState` stays tool-owned — the problem statement counts it as a fifth encoding, but the lamp helper does not replace it).
- bash carries its structured result (command, output, exit/signal/timeout/timedOut — cwd stays out of the projection: `presentationMeta` is a pure function of args and the canonical value, and the canonical bash result carries no cwd, so the resolved workdir never enters the value; cwd renders from the call view as the bridge resolves it against the session cwd) via `presentationMeta`; its `parseExitStatus` text round-trip is gone; the model-facing bash text is unchanged (snapshot). A single-command call renders with one lamp; a joined multi-command call composes Segments directly under one lamp, no `Group` (per-command `Group`s are the deferred executor change); the single-command case is visually equivalent to today's `TerminalBlock` (snapshot).
- The seven built-in registrants register through `registerToolView`; `ask_user_question` and `todo_write` set `views: ['chat']` (snapshot unchanged).
- One gutter width per `ToolCard` aligns every Segment's body; line numbers are always visible; empty and input-less segments collapse per the rules; per-segment IN/OUT copy works.
- Changing a converted tool's rendering touches only that tool's registrant module (demonstrated by 1d touching no bash file); no central render dispatch and no client-side render-kind union exist after PR 2 (the host-side `ToolCallView`/`ToolResultView` union and ui-tool's keyed slot dispatch are preserved, per the Proposal's increment scoping).
- The full test matrix ships (unit per-file 100%, real-API e2e, keyless snapshot, web-browser snapshot where the surface applies, smoke, CI gates, sandbox), including a keyless snapshot through a real runnable example asserting the assembled transcript. Coverage concentrates in the PRs with a real tool producing a transcript.

## Risks

- **Scope.** This adds a package, rewrites every registrant through a facade and the primitives, and retires ToolRow's card chain. It is staged (package → bash → facade adoption → one tool → the rest) to bound each PR, and PR 1a (package creation) is behaviour- and pixel-neutral to de-risk the move.
- **Wire is untrusted.** `sessions.schema.ts` validates only `for` + `card: string`; every registrant MUST re-narrow its view defensively, or a malformed payload crashes its row — the same discipline the card models keep today, now living in each registrant.
- **One key, two producers.** The `bash` key is shared by `tool-bash` and `tool-bash-persistent` (whichever a deployment mounts), so the `bash` registrant renders both from PR 1b on — it cannot wait for the persistent tool's deferred structured result. Its no-meta text-reconstructable path is not optional polish but the compatibility shape the persistent producer relies on; PR 1b owns that test. (`tool-pwsh` has no keyed `pwsh` registrant today and keeps its own host-side presenter until its PR 2 migration, so the `bash` registrant never renders it — keyed dispatch is by wire tool name and `pwsh` ≠ `bash`, and the shared `parseExitStatus` seam it consumes is code, not a render path.)
- **Windowed replay with the call out of frame.** A paginated replay window can start at a `tool/result` whose `tool/call` fell outside it; the host skips `presentResult` and the client node has `call: null`, so there is no args JSON for the generic fallback and no `command` for bash's no-meta path to reconstruct from. Both degrade to result-text-only (no IN segment) for that node until an upward page brings the call in — a bounded, self-healing degradation, not a wrong render.
- **Replay purity.** Presentation methods and the lamp helper run on the live and replay paths and must stay pure functions of the view (args + result meta), no I/O, clock, or session state — the purity contract covers presentation methods ([AGENTS.md §Conventions](../../../../AGENTS.md#conventions), [adding-a-tool.md](../../../../docs/cookbook/adding-a-tool.md)); registrants are UI adapters that consume explicitly-passed snapshots.
- **Consistency by convention.** Because a tool may restructure its whole row, row-to-row visual consistency rests on the built-ins following the default helper rather than a central lock; the snapshot suite is what catches a drifting row.
- **What is given up.** Uniform status means the cards that today show *no* in-card status gain a lamp; for genuinely unobservable outcomes the honest value is grey, never a manufactured green. Four shapes are deferred: per-command `Group`s for a joined multi-command call; a structured per-round result so a *successful* persistent/PTY round can read as done (today a zero-exit round leaves no marker and those tools carry no structured result, so a pure presenter reconstructs only a failed persistent-shell round, and no raw-PTY round at all); nested-`Group` recursion; and the persisted abort code for `run_code` sub-calls, so a cancelled sub-call stays honest red rather than amber. Until they land, a multi-command call composes Segments directly under one lamp (no `Group`), each interactive round is its own card showing error on a non-zero exit and grey on success, and a timed-out command reads as a signal/exit red until PR 1b's structured bash result feeds `timedOut` into the lamp.
- **AGENTS.md drift.** [AGENTS.md §Conventions](../../../../AGENTS.md#conventions) still lists three card kinds; the render-intent union already has more. This work should update that line and the render-intent design note in the same PR.

## Supersedes

This proposal is an increment on the implemented ui-tool boundary, so it amends rather than replaces the notes that own the pieces it builds on. The [Client Tool presentation ownership](../../implemented/architecture/2026-08-08-client-tool-presentation-ownership.md) and [Client Conversation business-node assembly](../../implemented/architecture/2026-08-09-client-conversation-node-assembly.md) decisions stay current authority for the dispatch, the fallback, the card models, and the node assembly; this note does not restate or replace their ownership tables. Within the atomic views it does two things to existing decisions:

- It **builds** the `registerToolView` facade the [toolview dissolution note](../../implemented/architecture/2026-07-23-toolview-dissolution.md) deferred with a regret clause (once registrants reach three-to-five or a bulk-registration pattern appears), honouring that note's one-registration-model decision — ui-tool's seven registrants trip the clause. It does not supersede the note's slot-based registration model; the facade is sugar over `slots.register`.
- It **amends the render-intent records' implementation**, not their wire views: the render-intent union ([2026-07-02-tool-render-intent-union.md](../../implemented/architecture/2026-07-02-tool-render-intent-union.md)) and the per-card records keep their `card` tags, `presentationMeta` channels, and fallback semantics — those are the host-side boundary this proposal explicitly preserves. What changes is the *client* rendering of those views: the two-step status derivation now duplicated in `GenericToolCard` and `bash-sample` (the `ToolRowState`/`terminalFailed` pair in ui-tool's card models) is replaced by the lamp helper, and bash's `parseExitStatus` text round-trip (recorded by the [render-intent union](../../implemented/architecture/2026-07-02-tool-render-intent-union.md) and refined by [pwsh UI presentation matches bash](../../implemented/feature/2026-08-05-pwsh-ui-bash-parity.md)) is replaced by the structured `presentationMeta` for bash's own result, while the `@deepseek-ai/dsh-bash` seam stays alive for `tool-pwsh`.

Because this is an increment whose supersession is confined to the client render path and does not rewrite any note's decision, the reciprocal cross-links added in this PR are scoped to that amendment, not to the broader supersession the earlier draft asserted. The render-intent records whose *implementation* this proposal changes — the [render-intent union](../../implemented/architecture/2026-07-02-tool-render-intent-union.md) and [pwsh UI presentation matches bash](../../implemented/feature/2026-08-05-pwsh-ui-bash-parity.md) — each carry a reciprocal link naming this proposal (a blockquote under their Status lines, the same shape the union already uses for its ACP supersession), and this section names them in return. The ownership decisions this note builds on stay authoritative and take no link, and the sealed web-cards-toolrow note takes none either (a frozen artifact carries no supersession bookkeeping). The relationship is updated in place where each migration lands.
